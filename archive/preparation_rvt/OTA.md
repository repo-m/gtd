# #OTA

- Governance & Regulatory (SUMS/UN R156): Compliance is driven by the **RXSWIN** (Regulation Software Identification Number), which links software versions to vehicle certification (Re-certification might be needed)
    - **Traceability Chain:** Every update must trace from Requirement → SW Version → Unique Binary Hash → Passing HIL Test Report.
    - **Post-Update Validation:** The vehicle must send a confirmation to the Digital Twin (Cloud) detailing who authorized it, the HIL validation used, and the new RXSWIN.
    - **Configuration Integrity:** Automated checks must ensure SW/HW compatibility and identify which fleet segments require backward-compatible binaries.
- Technical Architectures & Strategies: Modern OTA moves beyond simple file transfers to robust deployment strategies.
    - **SOTA vs. FOTA:** Software-over-the-air updates specific components (SWC), while Firmware-over-the-air handles the "heavy lifting" of low-level system firmware.
    - **A/B Partitioning:** Uses a secondary memory partition as a safety net; if the new update fails, the system reverts to the stable version.
    - **Delta Updates:** To maximize efficiency, only the binary "diff" (differences) between the old and new versions is transmitted.
    - **The OTA Pipeline:** The **Cloud** manages the campaign, the **Gateway/TCU** acts as the "Postman" (downloading/verifying/decrypting), and the **Target ECU** is the receiver.
- Campaign Management & Fleet Health: Managing a rollout requires balancing speed with system stability.
    - **Safe State Enforcement:** Updates only trigger if the vehicle is in a predefined safe state (e.g., Parked, Gear in P, Battery > 20%).
    - **Rollout Strategy:** Utilize **Canary Releases** (small batches) before full fleet deployment.
    - **The "Kill Switch":** Ability to instantly terminate a campaign in the backend and push a revert command if issues arise.
    - **Scheduling & Bandwidth:** Use **Time-Slicing** and **TSN (Time-Sensitive Networking)** to prevent high-speed Ethernet updates from saturating the Gateway CPU and "starving" smaller CAN-bus ECUs.
        - Time-Slicing & Sequencing: Instead of flashing everything at once, you implement a staged sequence:
            - Stage A: Download all Delta packages to the Central Compute storage.
            - Stage B: Flash Zonal ECUs (CAN-FD) first or in parallel with limited Ethernet bandwidth.
            - Stage C: Flash the Central Compute (Ethernet) last, as it is the fastest and often the coordinator.
- Testing & Edge Cases: Validation must extend beyond the "Happy Path" to account for "Rainy Day" scenarios.
    - **HIL (Hardware-in-the-Loop) Stressors:** Testing updates under 80% bus load, 9V voltage drops, or interrupted pipes.
    - **Edge Case Resilience:** Handling corrupted downloads from weak cellelar signals, flash memory hardware degradation (write limits), and user interference during safe-state checks.
    - **Production (EOL):** The initial "Provisioning" of the RXSWIN at the factory must be optimized for speed to minimize production costs.
- Security & Cross-Functional Integration: Security must be robust but should not compromise vehicle availability.
    - **Security Evolution:** Transitioning from single #SFD (Software Feature Data) tokens to centralized **TLS tunnels**.
    - **Offline Fallback:** If certificate servers are down, technicians must be able to perform an **Offline Flash via OBD**, with SUMS data uploaded to the cloud later to maintain the audit trail.
    - **Cross-Functional Requirements:**
        - **Software:** Fixing UDS (Unified Diagnostic Services) timing.
        - **Hardware:** Ensuring CAN transceivers can handle increased bus speeds.
        - **Systems:** Updating the ICD (Interface Control Document) between the Gateway and Target ECUs.
